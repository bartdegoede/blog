# Ask my blog — Design

## Goal

A permanent `/ask/` page where readers ask a question and get (a) the most
relevant passages from the blog, via the existing in-browser potion semantic
search, and (b) a short, clearly-labelled summary written by a small language
model running **entirely in the reader's browser**. No server, no API key, no
download until the reader explicitly asks for one.

Plus a blog post about it, inspired by
[MicroLLM lab](https://stateofutopia.com/experiments/microllmlab/) (credited,
along with `yangqi0/petitgpt`), whose central question is: **how much better
would the summaries get if I rented a GPU or paid for hosted inference — and is
that worth it?**

## Decisions (locked)

- **Feature, not a demo**: a dedicated `/ask/` page, linked from the homepage
  search area ("Ask instead →") and from the post. Excluded from the search
  index and RSS.
- **Opt-in download**: nothing model-related is fetched until the reader clicks
  "Load". The homepage search box never triggers a model download.
- **Sources first (option B)**: retrieved passages are the primary result and
  render immediately; the model adds a ≤2-sentence summary above them,
  labelled "generated by <model>, may be wrong".
- ~~**Two model sizes, chosen by eval**, each ≤ ~350 MB~~ — **superseded
  2026-10-12 by the eval** (see `2026-10-12-ask-my-blog-results.md`): no
  ≤350 MB model was usable (0-3/30 faithful). New decision:
  - **Default model: Qwen3-0.6B** (q4f16, ~579 MB; 15/30 faithful).
  - **Demonstrators**: SmolLM2-360M, Gemma 3 270M, LFM2.5-350M, offered and
    clearly labelled as "see why size matters", not as recommended options.
  - Not offered: SmolLM2-135M (0/30), Gemma 4 E2B (3.1 GB; post-only reference).
- **Weights come from the Hugging Face Hub**, not GitHub Pages (Pages has a
  100 MB file / 1 GB site limit). Each model is pinned to an HF commit hash;
  the page notes that loading a model makes a request to huggingface.co
  (questions themselves never leave the browser).
- **Repetition penalty 1.15** with greedy decoding (`REPETITION_PENALTY` in
  `assets/js/ask/prompt.js`); without it the tiny models loop.
- **Runtime**: transformers.js (ONNX Runtime Web), WebGPU with automatic WASM
  fallback. WebLLM and wllama are covered in the post, not used on the page.
- **Big/hosted models are eval-only**: Gemma 4 E2B (~3 GB) and a hosted API
  model are measured as reference tiers; they never appear on `/ask/`.
- **Post angle**: these numbers, and what it would take to make the tiny
  models actually useful (sets up a possible follow-up post on fine-tuning).
- **Prices in USD.**
- **No reuse of MicroLLM lab code**: its repo states no license; we build on
  transformers.js directly and credit it as inspiration.

## Shipped (Part 2): where the page differs from the design below

The sections below are the original design. Where they disagree with this list,
this list (and the code) wins.

- **Sources-only first.** The question bar works from page load without a model:
  it shows the passages, and a summary appears once a model is loaded. The model
  status strip (Summaries off / loading / on) sits under the question bar.
- **Route:** `content/ask.md` with `layout: ask` → `layouts/_default/ask.html`
  (not `layouts/ask/single.html`). `noindex`, unlisted, excluded from the sitemap;
  linked from the homepage search box (the Part 3 post will link to it too).
- **Backend:** WebGPU only when the adapter has `shader-f16`; otherwise WASM,
  labelled "CPU · slow" with a "~30 to 60 s per answer" note. WASM is
  single-threaded (no COOP/COEP on GitHub Pages). Gemma 3 270M and LFM2.5-350M
  are `webgpuOnly` (their q4f16 uses an op with no WASM kernel) and are disabled
  on CPU. "Try slower mode (CPU)" exists only as a retry after a WebGPU load error.
- **Benchmark on load:** 64 tokens on WebGPU, 16 on WASM; results show in the
  status strip (tok/s) and its tooltip (first token), not a separate panel.
- **Two-sentence stop:** the worker clamps and interrupts generation at
  `MAX_SENTENCES` (2); the page shows only those sentences.
- **Citations:** leading `[n]` markers are stripped; inline `[n]` become links to
  the source card holding passage n (the "out of scope" note below is superseded).
- **Sources:** one card per post, with each matched section as a sub-item; snippets
  are cleaned of footnote refs and the index's repeated section heading.
- **Download progress:** one tile per ~4 MB (`tileCount`) plus a text label
  (`212 / 579 MB · 37% · ~40 s left`); no separate bar, no layer-count label. Under
  `prefers-reduced-motion` the tiles stay, only animation/transitions are dropped.
- **Stop:** on WebGPU a message interrupts generation; on WASM the worker can't
  see that message mid-generation, so Stop terminates it and reloads from cache,
  or offers "Reload model (N MB download)" when the model isn't cached.
- **Storage:** the page asks for persistent storage (best effort), warns before a
  download when quota is short, and says afterwards if the model wasn't kept.
- **Accepted trust boundary:** transformers.js is pinned (`@4.3.1/+esm`) but loaded
  with dynamic `import()` from jsDelivr, which can't carry SRI; jsDelivr also serves
  the ONNX Runtime WASM. The page's small print discloses jsDelivr and Hugging Face.

## Out of scope (v1)

- Using the model from the homepage search box (query expansion, result
  summaries). Mentioned in the post as "next"; if ever built, it may only use a
  model that is *already cached* and must never start a download.
- Chat history / follow-up questions. Each question is independent.
- Inline citation markers (`[1]`) in the summary — small models get them wrong;
  the source cards already show provenance.
- A user-selectable open model zoo.

## Page and load flow

Route: `content/ask.md` + `layouts/ask/single.html`.

States:

1. **Idle** — intro text; a read-only capability probe (WebGPU yes/no,
   `navigator.deviceMemory` if available); one card per offered model with
   name, download size, and a "Load" button. Cards for models already in the
   cache say "Cached — loads instantly".
2. **Loading** — the *model map* (see Loading UX) driven by transformers.js
   per-file progress. When loading completes, the benchmark runs automatically:
   fixed prompt, 64 generated tokens, recording time-to-first-token, tokens/s
   and backend (WebGPU/WASM). Results show in a "Your machine" panel.
3. **Ready** — question box, "Switch model", and "Delete downloaded models"
   (clears the transformers.js cache so readers control their storage).

Answer layout: source cards (post title, quoted passage, link to the post
section) render immediately; the summary box above them streams in.

Failure modes:

- Model load fails → clear error; sources-only search still works.
- No WebGPU → runs on WASM, labelled "slower mode".
- Neither WebGPU nor a viable WASM path → sources only (degrades to semantic
  search).

## Question → summary pipeline

1. **Retrieve**: query through `assets/js/semantic/` (unchanged); take the top
   4 chunks. Render source cards.
2. **Relevance gate**: if the best chunk's score is **below 0.45** (chosen in
   the eval; see results doc §3), or retrieval returns no passages, do **not**
   call the model. Show "I couldn't find this on the blog" plus the nearest
   results. The gate catches clearly off-topic questions only; near-misses
   still reach the model.
3. **Prompt**: `buildMessages` from `assets/js/ask/prompt.js` (the model's own
   chat template; Qwen3 with `enable_thinking: false`). System prompt: answer in
   at most 2 sentences, only from the passages, say so if they don't answer the
   question. Passages trimmed to `MAX_PASSAGE_CHARS` (4,800).
4. **Generate**: greedy decoding (`do_sample: false`), `MAX_NEW_TOKENS` (120),
   `repetition_penalty: REPETITION_PENALTY` (1.15), streamed via transformers.js
   `TextStreamer`. A "Stop" button aborts. Constants come from `prompt.js`; never
   duplicate them.
5. **Post-process for display**: strip a leading passage marker (`[1]`) and
   consider showing only the first two sentences (results doc §6).

The model runs in a **Web Worker**; it posts progress, tokens and benchmark
results to the page.

### Code layout (new; existing search code untouched)

- `assets/js/ask/worker.js` — model load, benchmark, generation.
- `assets/js/ask/prompt.js` — chunk budgeting + prompt assembly; pure
  functions, unit-tested with `node --test`, and shared with the eval harness.
- `assets/js/ask/page.js` — UI states, rendering, cache management.

Bundled with `js.Build` as an ES module, following the pattern in
`layouts/shortcodes/benchmark.html`.

## Loading UX

| Phase | Typical duration | Treatment |
|---|---|---|
| First download | tens of seconds – minutes | **Model map**: grid of tiles, one per weight shard/layer, labelled with layer count and parameter count; tiles fill as bytes arrive (real progress) |
| Load from cache | ~1–5 s | Same map, filling quickly |
| Retrieval | < 1 ms | None — sources just appear |
| Prefill | <1 s WebGPU, ~2–6 s WASM | **"Reading" sweep**: soft highlight sweeps across the visible source cards, "Reading 4 passages (~1,100 tokens)…"; 2-line skeleton in the summary box until the first token |
| Generation | streaming | Blinking cursor + live tok/s counter ("38 tok/s · WebGPU") in the summary box corner |

**Download progress bar (always shown, alongside the model map):**

- Determinate bar with text: `212 / 579 MB · 37% · ~40 s left` plus current
  throughput. ETA from a smoothed rate over the last few seconds.
- The overall total is known from the first byte: each offered model ships with
  its pinned file list and byte sizes (`revision`, `files`, `total_bytes` in
  `scripts/ask_eval/candidates.json`),
  so the bar does not jump as transformers.js discovers files one by one.
  Per-file `progress` events from the `progress_callback` feed the loaded count.
- Cached model: bar fills near-instantly, labelled "Loading from cache".
- After 100%: a separate indeterminate "Preparing model…" step (session
  creation / WebGPU shader compile) so the bar never sits at 100% looking stuck.
- Failure mid-download: bar shows the error and a Retry button; files that
  finished are already cached and are not re-downloaded.

All animations respect `prefers-reduced-motion` (the model map is hidden; the
progress bar and static text remain).

## Eval

> **Status: done.** This section is the eval as designed. Where the outcome
> overrode it (shipped models, gate threshold, Qwen tiers), the Decisions
> section above and `2026-10-12-ask-my-blog-results.md` are authoritative.

Goal: pick the two shipped models, tune the relevance threshold, and produce
the cost/quality curve for the post.

### Question set (~45)

- The 30 labelled queries from the semantic-search eval
  (`examples/degoe-de/queries.yaml` in sss_eval), rephrased as questions where
  needed; each keeps its known relevant posts.
- ~15 new **negatives** the blog does not answer — a few far-off ("how do I
  bake sourdough?"), mostly near-misses ("how do I add search to a Jekyll
  site?").
- Generated by Claude, reviewed by the author; the post says so.

### Arms

| Tier | Arms | Measured cost |
|---|---|---|
| In-browser (≤ ~350 MB) | SmolLM2-135M-Instruct, SmolLM2-360M-Instruct, Gemma 3 270M-it, LFM2.5-350M (Qwen3-0.6B and Qwen2.5-0.5B turned out over budget: Qwen3 was kept as a "midsize" reference and later chosen as default; Qwen2.5 was not run) | $0; download size |
| Large local / rented GPU | Gemma 4 E2B-it (~3 GB q4f16) | $0 in-browser; USD/1,000 questions for a realistic small cloud GPU at this blog's traffic |
| Hosted inference | Claude Haiku 5.5 | USD/1,000 questions from measured token usage |

**Feasibility gate (first step)**: verify each candidate on its Hugging Face
`onnx-community` (or equivalent) page — actual q4 size and transformers.js
compatibility. Drop anything that doesn't load; record why. Qwen3.5-0.8B is
excluded up front (no official ONNX build) and mentioned under WebLLM in the
post.

### Harness

A Node script using the same ONNX files and the same `prompt.js` as the
browser (CPU backend), greedy decoding, retrieval from the same potion index.
Output: one JSONL row per (arm, question) with chunks used, summary, TTFT,
tokens/s, and token counts.

### Scoring

A Claude judge labels each summary against the chunks it was given:

- **faithful** — every claim supported by the passages
- **unsupported** — contains at least one claim not in the passages
- **non-answer** — declines or rambles without answering

The author spot-checks ~20 judgements, **deliberately including the Haiku
arm** (self-preference risk); agreement rate is reported in the post. The
judge uses a different Claude model than the Haiku arm.

### Outputs / decisions

1. **Relevance threshold**: ~~chosen to block nearly all near-miss
   negatives~~. Superseded: near-miss scores overlap answerable ones, so the
   eval reports a sweep and the author chose **0.45** (blocks off-topic only;
   9/15 negatives pass, 2/30 answerable rejected).
2. **Shipped models**: ~~"Small" = smallest arm with ≥ ~75% faithful;
   "Better" = most faithful arm ≤ ~350 MB~~. Superseded: no ≤350 MB arm
   exceeded 3/30; see Decisions (Qwen3-0.6B default + three demonstrators).
3. **Cost/quality table** across all tiers: % faithful, % unsupported,
   latency, USD per 1,000 questions, reader download size.

### Browser runtime measurements

A separate headless-Chromium run (Node can't measure WebGPU) records
WebGPU vs WASM TTFT and tokens/s for the shipped models, plus the same small
model (SmolLM2-135M) under WebLLM and wllama for the "other runtimes" table.
If a runtime is too painful to set up, say so and describe it qualitatively.

## Post

Working title: *"Running RAG with a (small) language model in the
browser"* — follow-up to the semantic-search post.

1. Hook: MicroLLM lab (credited) + "my search already finds the right
   passages; can a tiny model summarize them?"
2. What runs on your machine: in-post benchmark widget (shortcode pattern).
3. How `/ask/` works: retrieval → gate → prompt → streaming, with a diagram.
4. The eval: cost/quality curve, best and worst summaries.
5. Is renting a GPU or paying for an API worth it? The answer, in numbers.
6. Other ways to run this: WebLLM, wllama, measured comparison table.
7. Try it: link to `/ask/`.

Afterwards: related-posts suggestions presented for confirmation (never
auto-filled), and narration via `scripts/text_to_speech.py`.

### Style

Match the recent posts (e.g. `2026-07-11-narrating-my-blog-with-a-local-model.md`,
`2026-07-10-semantic-search-in-your-browser.md`):

- First person, conversational, a bit wry; opens by linking back to earlier
  posts and the "why now".
- **Em dashes sparingly**: the existing posts use about one per 1,500-3,000
  words. Prefer commas, semicolons, colons, parentheses or a new sentence.
- Inline links to tools, models and earlier posts; asides go in footnotes
  (`[^name]`).
- `<!-- more -->` after the intro; audio shortcode at the top once narrated.
- Front matter per CLAUDE.md (title, date, slug, categories, keywords,
  description, `related:` once confirmed).

## Testing

- `prompt.js`: unit tests (budget trimming, template assembly, gate logic) with
  `node --test`; the existing 107 tests stay green.
- Worker/page: headless-Chromium smoke test — load the Small model, ask one
  answerable and one negative question, assert sources render, summary
  streams for the first, gate fires for the second.
- Manual: WASM fallback (WebGPU disabled), reduced-motion, cache delete.
